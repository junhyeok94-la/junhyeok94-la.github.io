# Pop Talk 로그 전체 검토와 사례 선정

## 검토 범위

제공된 압축 로그 5개를 모두 읽고 JSON 레코드·노드 실행·오류·헬스체크를 분류했다.

| 파일 | 전체 레코드 | 노드 완료 이벤트 | 헬스체크 |
| --- | ---: | ---: | ---: |
| pop_talk_chatbot_10.json.gz | 581 | 91 | 482 |
| pop_talk_chatbot_11.json.gz | 480 | 0 | 480 |
| pop_talk_chatbot_15.json.gz | 1,139 | 239 | 486 |
| pop_talk_chatbot_16.json.gz | 696 | 138 | 485 |
| pop_talk_chatbot_17.json.gz | 582 | 31 | 487 |
| 합계 | 3,478 | 499 | 2,420 |

동일한 수집 시각·메시지가 중복된 48개 레코드를 제외하면 고유 레코드는 3,430개다. 중복 기록은 15번 파일에 있다. 이는 요청 수나 성공률을 뜻하지 않는다. 특히 11번 파일은 전부 헬스체크이므로 추천·검수 사례의 증거로 사용하지 않았다.

같은 프로세스의 입력 검증부터 응답 확정까지 연결되는 후보 경로를 비교했다. 일괄 수집으로 같은 초의 로그 행 순서가 실제 노드 순서와 다를 수 있고 모든 행에 요청 ID가 있지는 않으므로, 연결이 불명확한 경로는 성과 근거로 사용하지 않았다. 공개 JSONL은 실행 순서를 새로 구성하지 않고 원래 행 순서를 유지한다.

## 선정 기준

- 모호한 질문이나 점수만으로 끝나는 기록보다 입력 조건과 실제 조회 방식이 드러나는 기록 우선.
- 모델 검수 점수와 코드 근거 검증 결과를 구분.
- `passed=true`만 보고 재시도 성공이나 정확도 개선으로 판단하지 않음.
- 재시도 후 실패한 사례는 제한 응답·검증 경계의 구현으로 설명하고 추천 품질 개선으로 포장하지 않음.
- 다른 파일의 서로 다른 실행을 하나의 성공 경로로 연결하지 않음.
- 현재 사이트에 필요한 원문 행만 발췌하고 호스트명·로그 경로만 마스킹.

## 선정한 세 사례

### 1. 요청 조건 구조화와 벡터 검색

17번 파일 484~485행. QueryPlan의 `countries=[한국]`, `max_runtime_minutes=120`, 제외 키워드, `requires_vector_search=true`와 다음 추천 조회의 `search_mode=vector`, 후보 5편을 연결해 보여준다.

저장된 영화 데이터와 대조하면 후보 5편은 모두 한국 제작이며 상영시간은 각각 111·82·44·109·97분이다. 이 사례는 조건 구조화와 검색 결과의 국가·시간 조건을 설명한다. 분위기나 감정적 적합성까지 검증한 우수 추천 사례라는 뜻은 아니다. 검수 100점은 성과 수치로 사용하지 않았다.

### 2. 리뷰 요약의 SQL 분기

17번 파일 371·374행. `intent=review_summary`, `requires_vector_search=false`와 `search_mode=representative_sql`, `exclude_spoilers=true`, `review_count=6`을 보여준다.

관련 리뷰 요약 실행에는 검수 정책으로 일부 경고를 비치명 처리한 경우가 있으므로 해당 검수 통과를 품질 개선 근거로 제시하지 않는다. 선정한 원문은 의도별 조회 방식과 스포일러 제외 조건의 적용만 입증한다.

### 3. 근거 없는 URL 검출과 제한 응답

16번 파일 416·425행. `source_mismatch`, `evidence_validation_passed=false`, `passed=false`로 근거 없는 URL을 검출한 실행과 `review_failed_grounded_recommendations` 종료 상태를 보여준다.

동일 실행의 주변 기록에서 답변 재생성과 재검수, 재시도 한도 도달을 확인했다. 보관 중인 챗봇 코드에서도 해당 종료 상태가 생성 답변 대신 DB 조회 영화 목록을 사용하는 분기임을 확인했다. 정상 검수를 통과한 사례가 아니라 잘못된 생성 응답을 그대로 반환하지 않는 경계 처리 사례다.

## 기존 사례와 제외 사유

- 기존 10번 파일의 ‘오늘 뭐 보지’ 재검색 사례는 모호한 요청에 제목의 ‘오늘’과 연관된 후보가 검색돼 기능의 장점을 보여주기 어렵다. 재검색 후 점수 상승을 품질 개선으로 설명하지 않음.
- 기존 배우 요청의 의도 불일치·안전 종료는 실패 경계는 보여주지만 검색 방식·데이터 처리의 특징을 충분히 설명하지 못해 대표 사례에서 교체.
- 15번 파일 일부 실행은 HTTP 429 뒤 규칙 검수로 전환돼 100점을 받는다. 모델 검수 통과나 정확도 개선 사례로 제외.
- 17번 파일 리뷰 요약 중 `passed=true`임에도 피드백에 근거 없는 주장이 지적된 경우가 있다. 완화된 검수 정책이 기록되어 있어 성공 점수만 홍보하지 않음.
- 서로 다른 실행의 실패와 성공을 이어 붙여 개발 후 개선 효과로 표현하지 않음. 이 로그만으로 버전별 정확도·개선율은 산출하지 않음.

## 포트폴리오 반영

데이터 로그를 사례 제목 → 처리 설명 → 원문 로그 순서로 구성했다. 첫 사례만 펼쳐 보여주며 나머지는 필요할 때 확인할 수 있다. ‘요청 의도별 검색 방식 분리’와 ‘근거 검증과 재시도 제한’ 항목에서 해당 로그로 직접 이동하도록 연결했다. 원문의 JSON 필드 순서와 내용을 보존했고, 원문 파일 링크도 제공한다.
